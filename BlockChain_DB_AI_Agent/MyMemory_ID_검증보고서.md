## 0. 아이디어 상세 설명 (먼저 읽기)

MyMemory ID는 한마디로, **여러 AI 서비스에 흩어진 개인 맥락(기억)을 사용자 중심으로 연결하고 통제하는 메모리 인프라**다. 현재 사용자는 ChatGPT, Claude, 로컬 LLM, 업무용 봇 등을 오가며 같은 배경 정보를 반복 입력해야 한다. 이 아이디어는 그 반복을 줄이고, AI가 사용자 맥락을 일관되게 이해하도록 만드는 데 초점을 둔다.

핵심은 단순 저장소가 아니라, 아래 3가지를 동시에 제공하는 것이다.

1. **기억의 이동성(Portability)**
- 특정 AI 앱에 종속되지 않고, 사용자가 허용한 범위에서 다른 AI 채널에도 같은 맥락을 재사용한다.

2. **기억의 통제권(Control)**
- 사용자가 메모리 단위로 공개 범위, 접근 가능 AI, 보유 기간, 삭제 여부를 직접 관리한다.

3. **기억의 신뢰성(Trustability)**
- 왜 이 기억이 응답에 쓰였는지, 누가 언제 접근했는지 확인 가능한 감사 흐름을 제공한다.

서비스 흐름은 다음과 같다.

1. 사용자가 대화 중 중요한 정보를 수동 저장하거나, 시스템이 저장 후보를 제안한다.
2. 저장된 기억은 의미 기반 검색이 가능하도록 벡터화되어 분류된다.
3. AI 호출 시 정책 엔진이 권한을 검사한 뒤, 관련 기억만 선별해 컨텍스트로 주입한다.
4. 사용자는 대시보드에서 기억의 출처, 사용 이력, 만료일, 권한을 수정하거나 즉시 삭제/내보내기 할 수 있다.

즉, MyMemory ID의 본질은 "신원 인증 서비스" 자체가 아니라, **AI 시대의 개인 맥락 데이터 레이어**다. DID/블록체인은 초기 필수 요소라기보다, 추후 고신뢰 환경(B2B/B2G)에서 감사 가능성과 상호 검증을 강화하는 확장 수단으로 보는 것이 현실적이다.

## 1. 요약 결론

MyMemory ID는 방향성은 매우 유망하지만, 현재 제안 범위 그대로는 초기 실패 확률이 높다. 핵심 리스크는 `기술 과잉`, `규제 과잉`, `UX 과잉`이며, 성공 가능성을 높이려면 1단계에서 모바일 신분증/온체인 결합을 필수로 두지 말고, 먼저 **AI 메모리 포터빌리티 + 사용자 통제권** 문제를 해결하는 경량 MVP로 시작해야 한다.

---

## 2. 시장 필요성 검증

### 2-1. 실제 Pain Point
- 여러 AI를 병행 사용 시 대화 맥락이 끊김
- 앱/모델별 대화 기록 파편화
- 개인화가 누적되지 않아 반복 설명 비용 발생

### 2-2. 판단
- 시장 필요성: 높음
- 사용자의 실질 수요: DID 자체가 아니라 "어디서든 동일한 개인 맥락 유지"

---

## 3. 기존 서비스 대비 차별성

### 3-1. 유사 시도 영역
- 플랫폼 내 메모리: ChatGPT Memory, Claude 프로젝트/메모리
- 개인 지식 저장/회수: Rewind, Mem.ai, PKM+RAG 계열
- 개발자용 메모리 미들웨어: Mem0, LlamaIndex/LangChain 기반 구현체
- 신원/자격 증명: DID/VC 지갑/인증 생태계

### 3-2. 차별화가 성립되는 조건
다음 2가지를 실제 UX로 증명하면 강한 차별화가 가능하다.

1. **Cross-AI Memory Portability**: 모델/앱이 달라도 기억 연속성 유지
2. **User-controlled Policy Layer**: 메모리 단위 접근 권한/유효기간/공개 범위를 사용자가 직접 제어

블록체인 접근 로그는 보조 차별화 요소로는 유효하나, 초기에 사용자 효용으로 직결되지 않으면 비용만 증가한다.

---

## 4. 기술적으로 가장 어려운 부분

1. 장기 기억 후보 추출 정확도
- 대화 중 무엇을 저장할지 자동 분류하는 문제

2. 메모리 정합성 관리
- 오래된 기억, 충돌 기억, 잘못된 기억 정리(merge/forget/decay)

3. 정책 강제 엔진
- "어떤 AI가 어떤 기억까지 접근 가능한가"를 실시간으로 강제

4. 멀티 모델 호환 계층
- GPT/로컬 LLM/모바일 앱별 프롬프트/토큰/도구 규약 차이 대응

5. 저지연 RAG
- 대화 품질을 유지하면서 검색/주입 지연을 최소화

---

## 5. 구현 시 병목 가능 지점

1. 온보딩 병목
- DID/모바일 신분증 필수화 시 초기 이탈 급증

2. 권한 설정 병목
- 개인정보 공개 범위 설정이 복잡하면 기능 미사용

3. 비용 병목
- 임베딩 + 벡터 검색 + 암호화 + 감사 로그 누적 비용

4. 신뢰성 병목
- 잘못된 기억 회수 시 서비스 신뢰 붕괴

5. 연동 병목
- 외부 AI API 정책 변경/제한으로 기능 불안정화

---

## 6. 사용자 소유권 수요 검증

사용자는 "소유"라는 개념어보다 아래 권리를 원한다.

- 삭제권(Forget)
- 내보내기(Export)
- 서비스 간 이동성(Portability)
- 민감정보 접근 통제

즉, 구매 포인트는 철학적 소유권보다 **실행 가능한 통제권**이다.

---

## 7. Docker 기반 개인 서버 UX 적합성

일반 사용자 대상 기본 UX로는 부적합하다.

- 서버 운영/업데이트/백업/보안 패치 부담
- 장애 시 사용자 스스로 복구하기 어려움

권장 구조:

1. 기본: 관리형 클라우드
2. 옵션: 원클릭 Self-host(고급 사용자/기업)
3. 로컬 전용: 실험 기능으로 제공

---

## 8. 블록체인 필수성 평가

초기 MVP 단계에서는 필수가 아닐 가능성이 높다.

- 메모리 저장, 권한 제어, 감사 로그는 전통 아키텍처로 구현 가능
- 온체인은 비용/복잡성/규제 검토를 동반

온체인 필요성이 커지는 조건:

1. 다기관 간 상호불신 환경
2. 제3자 검증 가능한 감사 추적이 계약상 요구됨
3. 검증 이익이 운영 비용을 상회함

---

## 9. Open DID / OmniOne Chain 활용성

### 장점
- 국내 공공/금융/교육 연계 시 신뢰 프레임 구축에 유리
- VC 기반 선택적 공개(Selective Disclosure) 설계 가능

### 한계
- 일반 B2C 초기 단계에서는 사용자 체감 가치가 약할 수 있음
- 파트너/생태계 의존도가 높음

### AI 에이전트 결합 시 효율
- 기존 신분증 검사 형식을 AI 에이전트 인증 단계에 재사용하면, 신규 인증 체계를 처음부터 설계하는 비용과 운영 복잡도를 줄일 수 있음
- 검증된 신원 속성을 기반으로 권한 범위를 자동 적용하면, 에이전트가 필요한 데이터만 최소 범위로 접근해 응답 품질과 보안을 동시에 개선할 수 있음
- 사용자 입장에서는 반복 본인확인 절차를 줄이면서도, 상황/역할/민감도에 맞춘 개인화 AI 서비스를 더 빠르게 이용할 수 있음

### 판단
- B2G/B2B2C에서는 전략적 가치가 있음
- B2C 초기 PMF 단계에서는 과투자 위험이 큼

---

## 10. 개인정보 및 법적 리스크

핵심 리스크는 "장기 기억 데이터 축적" 자체에서 발생한다.

1. 목적 제한/최소 수집 원칙 준수 필요
2. 민감정보 처리 동의 및 보유기간/파기 절차 명시 필요
3. 해외 이전(LLM API) 및 위탁 처리 구조 점검 필요
4. 접근 기록, 침해 통지, 감사 대응 체계 필요
5. 자동화된 프로파일링 관련 설명 가능성 확보 필요

실무적으로는 법률 검토와 보안 아키텍처 설계가 제품 설계와 동시에 진행되어야 한다.

## 11. 초기 MVP 단순화 권고

### 11-1. 반드시 포함
1. 이메일/소셜 로그인
2. 메모리 저장(수동 저장 + 반자동 추천)

4. 삭제/내보내기/권한 대시보드

### 11-2. 초기 제외
- 모바일 신분증 실연동
- 온체인 필수 로깅
- Docker 자가서버 기본값

### 11-3. 검증 KPI
- 30일 유지율
- 메모리 재사용률
- 반복 설명 시간 절감율
- 권한/삭제 기능 실제 사용률

## 12. 현실적인 BM(수익 모델)

1. B2C 구독
- Free: 저장량/연동 모델 수 제한
- Pro: 고급 정책 제어, 자동 메모리 정리, 고급 내보내기

2. B2B API/SDK
- AI 앱/에이전트에 Memory-as-a-Service 제공

3. Enterprise
- 전용 VPC/온프레미스, 감사 로그, 규제 대응 패키지

권장 순서: B2C 문제 검증 -> B2B SDK 확장

## 13. AI 산업 흐름 적합성

적합성이 높다.

- 멀티모델 환경 확산
- AI 에이전트 기반 워크플로 확장
- 개인 맥락 데이터 레이어 중요성 증대

다만 승부는 모델 성능 자체보다, 데이터 통제권/연동성/UX 레이어에서 갈릴 가능성이 높다.

---

## 14. 글로벌 유사 사례

완전히 동일한 형태는 드물지만, 다음 축의 유사 사례가 존재한다.

1. 플랫폼 내 메모리 기능 (ChatGPT, Claude)
2. 개인 데이터 인덱싱/리콜 (Rewind 계열)
3. 개발자 메모리 인프라 (Mem0, LlamaIndex memory 등)
4. DID/VC 기반 디지털 신원 솔루션

공백 지점은 "AI-agnostic 메모리 + 사용자 정책 통제 + 실사용 UX"의 결합이다.

---

## 15. 창업 아이템 성공/실패 가능성

### 성공 가능성 시나리오
1. 여러 AI에서 맥락 연속성이 명확히 체감됨
2. 권한/삭제/내보내기가 매우 쉬움
3. 개발자/파워유저 중심 커뮤니티 확산
4. 이후 B2B SDK로 확장

### 실패 가능성 시나리오
1. DID/체인 중심 메시지로 사용자 가치 전달 실패
2. 온보딩 복잡성으로 초기 이탈
3. 기억 품질 문제로 신뢰 붕괴
4. 개인정보 사고/규제 리스크 현실화
5. 단위경제성 악화(추론/저장/운영비)

냉정한 판단:
- 현재 설계 그대로: 실패 확률 높음
- MVP 단순화 + 단계적 고도화: 성공 확률 유의미 상승

---

## 16. 대학 창업 경진대회 관점

### 강점
1. AI + 보안 + 신원 결합 스토리의 임팩트
2. 사회적 이슈(데이터 주권/프라이버시)와 정합성
3. 데모 시연 효과(기억 연속성 체감)

### 약점
1. 범위 과대(실행력 의심 유발)
2. 법/인증 관련 현실성 질문에 취약
3. "왜 블록체인이 필수인가"에 대한 방어 부담

대회 전략:
- "블록체인 필수" 대신 "검증 가능한 신뢰 옵션"으로 포지셔닝
- 기술 용어보다 사용자 시간 절감 KPI를 전면 배치

## 17. 관점별 종합 분석

### 기술적 관점
- 강점: 개인화 컨텍스트 레이어라는 성장 축에 정렬
- 약점: 메모리 품질관리/정책 강제 엔진이 핵심 난제

### 사업적 관점
- 강점: B2C에서 B2B로 확장 가능한 구조
- 약점: 초기 타깃 세분화 실패 시 PMF 도달 지연

### 사용자 경험 관점
- 강점: "기억되는 AI"가 제공하는 강한 반복 사용 동기
- 약점: 인증/권한/서버 운영 복잡성은 즉시 이탈 요인

### 보안/규제 관점
- 강점: 신뢰성 아키텍처를 제품 차별화로 전환 가능
- 약점: 장기 기억 데이터 축적은 사고 시 피해 규모가 큼

## 22. 최종 제언

성공의 핵심은 블록체인 도입 여부가 아니라 다음 질문에 대한 실증이다.

"사용자가 어떤 AI를 사용하든, 본인 동의 하에 정확하고 안전하게 개인 맥락이 이어지는가?"

이 질문에 MVP로 명확한 "Yes"를 만든 뒤, DID/VC/온체인 검증을 고도화 단계에서 결합하는 것이 가장 현실적인 창업 경로다.

## 23. MVP 제작 가이드 (실행형)

본 섹션은 "MyMemory ID를 실제로 어떻게 만들 것인가"에 대한 빌드 순서 중심 가이드다. 원칙은 단순하다.

1. 먼저 "기억이 이어져서 편하다"를 증명한다.
2. 다음으로 "사용자가 통제할 수 있다"를 증명한다.
3. 마지막에 DID/체인으로 신뢰를 확장한다.

### 23-1. MVP 목표

1. 반복 설명 감소
- 같은 맥락을 여러 번 입력하지 않게 한다.

2. 사용자 통제 가능
- 저장/삭제/공유 범위를 사용자가 직접 관리한다.

3. 멀티 채널 재사용
- 최소 2개 AI 채널에서 같은 기억이 재활용된다.

### 23-2. 포함/제외 범위

포함:

1. OAuth 기반 로그인(구글/이메일)
2. 수동 저장 + 반자동 저장 제안
3. 벡터 검색 기반 기억 회수(RAG)
4. 권한 태그(개인/업무/민감)
5. 삭제/내보내기/접근 기록 확인
6. AI 채널 2개 연동

제외:

1. 모바일 신분증 실연동
2. DID 필수화
3. 온체인 필수 기록
4. Docker 자가서버 기본 제공

### 23-3. 8주 빌드 로드맵

1주차: 문제와 시나리오 고정

1. 타깃 사용자 15명 인터뷰
2. 반복 설명 시간 낭비 데이터 수집
3. 핵심 시나리오 3개 확정

2주차: 코어 데이터 플로우 구현

1. 사용자/대화/메모리 저장 스키마 구축
2. 수동 저장 버튼과 메모리 목록 화면 구현
3. 기본 검색 + 프롬프트 주입 연결

3-4주차: 기억 품질 개선

1. 저장 후보 자동 추천
2. 중복 제거 규칙
3. 오래된 기억 감쇠 규칙
4. 충돌 기억 우선순위 규칙

5주차: 통제 UX 완성

1. 메모리별 권한 태그 편집
2. 삭제/복구/내보내기 UX
3. "왜 이 기억이 사용됐는지" 설명 UI

6주차: 멀티 AI 연동

1. 두 번째 AI 채널 연결
2. 동일 사용자 기억 교차 재사용 검증
3. 지연 시간 최적화

7주차: 보안/운영 안정화

1. 암호화 저장 및 키 관리
2. 접근 로그와 이상 접근 탐지
3. 백업/복구 리허설

8주차: 클로즈드 베타

1. 30-50명 베타 운영
2. 핵심 KPI 측정
3. 유료 전환 가설 테스트

### 23-4. 권장 아키텍처

1. Client SDK
- 웹/모바일 챗 앱에서 대화 이벤트 수집

2. Memory Ingestion API
- 대화 내용을 받아 저장 후보 추출

3. Memory Policy Engine
- 민감도/범위/만료 정책 적용

4. Vector + Metadata Store
- 의미 검색과 정책 기반 필터링 동시 수행

5. Retrieval Gateway
- AI 호출 전 관련 기억만 선별 주입

6. Consent/Deletion Center
- 동의, 삭제, 내보내기 일괄 처리

7. Signed Audit Log
- 초기 오프체인 서명 로그, 이후 온체인 확장 가능

### 23-5. 최소 기술 스택

1. Backend: FastAPI 또는 NestJS
2. DB: PostgreSQL + pgvector
3. Queue: Redis + BullMQ/Celery
4. LLM: OpenAI 1종 + 로컬 LLM 1종
5. Auth: OAuth2/OIDC
6. Crypto: AES-GCM + KMS 기반 키 관리
7. Observability: OpenTelemetry + 구조화 로그

### 23-6. MVP 핵심 KPI

1. 메모리 재사용률
- 실제 응답에 기억이 반영된 비율

2. 반복 설명 감소율
- 동일 사용자의 평균 입력 길이/횟수 감소

3. 7일/30일 리텐션
- 기억 기능이 재방문을 유도하는지 확인

4. 통제 기능 사용률
- 삭제/권한/내보내기 기능 사용 빈도

5. 품질 체감 점수
- "맥락 이해가 좋아졌다" 사용자 설문 점수

### 23-7. 실패를 줄이는 운영 원칙

1. 자동 저장 100% 금지
- 반드시 사용자 승인 흐름을 포함한다.

2. 민감정보 기본 차단
- 기본값은 저장 안 함, 예외만 허용한다.

3. 기능 폭발 방지
- 초기에는 "저장-회수-통제" 3축 외 기능 추가 금지

4. 비용 상한 관리
- 사용자당 토큰/저장/검색 비용 상한선을 선제 설정

5. 법률/보안 병행
- 제품 개발과 동시에 개인정보/약관 검토를 진행
